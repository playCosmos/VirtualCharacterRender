# U2 — UI-independent remembered VRM session (first integrated slice)

**Base:** U1 Draft PR #44 at `10157e145b273465df502557bb0eef32477236af`. This is a stacked implementation; the user's instruction to *assume* the physical U1 gates have passed is a planning premise, **not** an assertion that physical evidence was collected. Nothing here merges PR #44, removes legacy uGUI, tags a release or claims hardware certification.

## Implemented

- `ModelSessionController` owns the unchanged `VCR.Character.LastSuccessfulPath.v1` PlayerPrefs key, restore candidate policy, successful interactive load persistence and explicit unload deletion. The original v1 key remains compatible; there is no new or silently migrated file format.
- `ApplicationRuntimeBootstrap` owns remembered-file restore in standalone Players after runtime initialization/configuration. Explicit `--vcr-vrm` has priority over the saved model; a failed explicit CLI load never silently loads a different remembered model. In both UI modes, an enabled Player bootstrap suppresses a second competing automatic restore; Editor and scenes without bootstrap retain their existing fallback.
- Supported automatic restores are VRM only. Missing or unsupported paths preserve the old reference and produce a single actionable inventory warning; no directory scan, FBX or thumbnail subsystem is implied. Unreadable VRM load failures are logged using basename and exception type, and optional scene state recovery returns to Ready *without resetting already applied render, camera or light configuration*. The old remembered path remains for explicit operator cleanup.
- U1 and legacy UI forward confirmed manual load and explicit unload to the same UI-independent preference API. CLI load and reload do not rewrite the last *manual* reference.
- A P1 regression checks genuine PlayerPrefs v1 interoperability, empty/missing/unsupported candidate decisions, CLI precedence, active-model precedence, success-only persistence and explicit unload, with integration source assertions.

## U2.2 — bounded, opt-in local VRM library

`ModelLibraryStore` persists an independently versioned `model-library.v1.json` in `Application.persistentDataPath`. The document has `Version: 1` and a bounded `Entries` array of `{ Path, Format: "vrm" }`. It is **not** a second authoritative active/remembered model session: `ModelSessionController` retains the unchanged `VCR.Character.LastSuccessfulPath.v1` key. The catalog does not automatically import CLI-loaded models, register successfully loaded models, scan a directory, load a VRM, or infer support for FBX.

- The UI Toolkit Sources panel provides explicit **Register path**, **Use selected path**, **Remove reference** and **Refresh library** actions. Using a path fills the existing editor without loading; the operator must still click **Load VRM**. Removing a reference does not delete model files, unload an active model, or clear the last-successful preference.
- Registration accepts only an existing, absolute, local `.vrm` path, never directories or an unimplemented FBX file. Reading a previously registered entry does not demand that its model file still exists: missing paths remain visible and removable. Paths are canonicalized; exact duplicates are rejected (case-insensitive on Windows). Maximum **128 entries**, maximum **4,096 characters per path** and **512 KiB per document**. No thumbnails, VRM contents, system-wide filesystem discovery or model binary copies.
- Catalog changes re-read and validate the entire on-disk document before atomic save, preserving a previous `.bak` generation. An unreadable, duplicate, malformed or future-version primary file is **never** treated as empty or overwritten by a normal Add/Remove action. A missing primary with existing `.bak` is likewise not a new catalog. A backup is **not applied automatically**: an operator must inspect and restore it manually, retaining original damaged files for diagnosis. No legacy v1 PlayerPrefs model path is ever rewritten while the catalog changes.
- The P1 Unity regression uses real filesystem and `PlayerPrefs`: verifies valid and invalid registrations, duplicate rejection, missing file retention, removal without source/remembered-model mutation, backup creation, corrupt JSON rejection, future-version protection, missing-primary+backup protection, and explicit manual backup recovery; the Toolkit action source contract is verified. These are synthetic fixture files, **not VRM import evidence**.

**Current scope limit:** synchronous local catalog operations on explicit operator clicks; there is no inter-process edit lock, filesystem watcher or concurrent-writer transaction. Do not run multiple application instances editing the same catalog simultaneously. Native Settings model page still uses its direct path UI; a platform-native model-gallery page remains a separate enhancement. Version 1 has no automatic migration path to unknown future versions.

## Legacy uGUI retirement — dependency inventory before deletion

The U1 application path retains `ApplicationUiController.cs` and its `NativeSettings` / `MockupDashboard` partials, Unity uGUI inputs and event handling, and older scene/Editor test references. The U2 library shares only the **runtime service and persisted v1 path**, not the legacy UI component. Do not delete the old UI or `com.unity.modules.ui` merely because U2's preference tests pass; removing older scenes, bindings, editor checks or standalone native Settings calls without a whole-repository dependency audit can break P0–P13. Legacy retirement requires a distinct coherent removal diff and exact-source Unity/Windows/macOS rebuild; no release or merge is implied.

## Remaining gate

U2 still needs a versioned **whole-session** record, opt-in session-record migration/rollback strategy, and tested multi-process catalog policy if required; the catalog document version alone does not deliver those features. No generic FBX adapter, simultaneous VRM instances, automatic filesystem indexing or source-file upload. Native runtime/CI runs on the exact U2 commit are required before acceptance. Physical U1 verification remains a user-authorized assumption only, not acquired evidence. PR #44 and stacked PR #45 remain Draft/unmerged.
