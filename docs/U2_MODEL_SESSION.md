# U2 — UI-independent remembered VRM session (first integrated slice)

**Base:** U1 Draft PR #44 at `10157e145b273465df502557bb0eef32477236af`. This is a stacked implementation; the user's instruction to *assume* the physical U1 gates have passed is a planning premise, **not** an assertion that physical evidence was collected. Nothing here merges PR #44, removes legacy uGUI, tags a release or claims hardware certification.

## Implemented

- `ModelSessionController` owns the unchanged `VCR.Character.LastSuccessfulPath.v1` PlayerPrefs key, restore candidate policy, successful interactive load persistence and explicit unload deletion. The original v1 key remains compatible; there is no new or silently migrated file format.
- `ApplicationRuntimeBootstrap` owns remembered-file restore in standalone Players after runtime initialization/configuration. Explicit `--vcr-vrm` has priority over the saved model; a failed explicit CLI load never silently loads a different remembered model. In both UI modes, an enabled Player bootstrap suppresses a second competing automatic restore; Editor and scenes without bootstrap retain their existing fallback.
- Supported automatic restores are VRM only. Missing or unsupported paths preserve the old reference and produce a single actionable inventory warning; no directory scan, FBX or thumbnail subsystem is implied. Unreadable VRM load failures are logged using basename and exception type, and optional scene state recovery returns to Ready *without resetting already applied render, camera or light configuration*. The old remembered path remains for explicit operator cleanup.
- U1 and legacy UI forward confirmed manual load and explicit unload to the same UI-independent preference API. CLI load and reload do not rewrite the last *manual* reference.
- A P1 regression checks genuine PlayerPrefs v1 interoperability, empty/missing/unsupported candidate decisions, CLI precedence, active-model precedence, success-only persistence and explicit unload, with integration source assertions.

## U2.2 — bounded, opt-in local VRM library

`ModelLibraryStore` persists an independently versioned `model-library.v1.json` in `Application.persistentDataPath`. The document has `Version: 1` and a bounded `Entries` array of `{ Path, Format: "vrm" }`. It is **not** a second authoritative active/remembered model session: `ModelSessionController` retains the unchanged `VCR.Character.LastSuccessfulPath.v1` key. The catalog does not automatically import CLI-loaded models, register successfully loaded models, scan a directory, load a VRM, or infer support for FBX.

- The UI Toolkit Sources panel provides explicit **Register path**, **Use selected path**, **Remove reference** and **Refresh library** actions. Using a path fills the existing editor without loading; the operator must still click **Load VRM**. Removing a reference does not delete model files, unload an active model, or clear the last-successful preference.
- Registration accepts only an existing, absolute, local `.vrm` path, never directories or an unimplemented FBX file. Reading a previously registered entry does not demand that its model file still exists: missing paths remain visible and removable. Paths are canonicalized; exact duplicates are rejected (case-insensitive on Windows). Maximum **128 entries**, maximum **4,096 characters per path** and **512 KiB per document**. No thumbnails, VRM contents, system-wide filesystem discovery or model binary copies.
- Catalog changes re-read and validate the entire on-disk document before atomic save, preserving a previous `.bak` generation. An unreadable, duplicate, malformed or future-version primary file is **never** treated as empty or overwritten by a normal Add/Remove action. A missing primary with existing `.bak` is likewise not a new catalog. A backup is **not applied automatically**: an operator must inspect and restore it manually, retaining original damaged files for diagnosis. No legacy v1 PlayerPrefs model path is ever rewritten while the catalog changes.
- The P1 Unity regression uses real filesystem and `PlayerPrefs`: verifies valid and invalid registrations, duplicate rejection, missing file retention, removal without source/remembered-model mutation, backup creation, corrupt JSON rejection, future-version protection, missing-primary+backup protection, and explicit manual backup recovery; the Toolkit action source contract is verified. These are synthetic fixture files, **not VRM import evidence**.

**Current scope limit:** synchronous local catalog operations on explicit operator clicks; there is no inter-process edit lock, filesystem watcher or concurrent-writer transaction. Do not run multiple application instances editing the same catalog simultaneously. Native Settings model page still uses its direct path UI; a platform-native model-gallery page remains a separate enhancement. Version 1 has no automatic migration path to unknown future versions.

## U2.3 — explicit, versioned model-session checkpoint

`ModelSessionSnapshotStore` provides a **manual-only** session checkpoint at `Application.persistentDataPath/model-session.v1.json`. The version-1 record separately captures `RememberedPath` / `RememberedFormat` from the existing authoritative PlayerPrefs key and `ActivePath` / `ActiveFormat` from the currently loaded scene, plus `CaptureReason = operator` and a UTC timestamp. The record is **not** automatically loaded into the scene or used as the startup restore authority. CLI precedence and the v1 legacy preference remain unchanged.

- The Toolkit Sources panel adds **Save session checkpoint**, **Inspect checkpoint**, and **Inspect backup**. It blocks snapshot writes when the scene is busy/unavailable or reports a loaded character without a reliable path. Inspect is read-only and displays only model basenames, not full local paths. The operator must independently select and load a VRM to change scene state.
- Captures use existing `BoundedTextFile.TryWriteUtf8Atomic` with a **32 KiB** limit and preserved `.bak`. A subsequent save first re-reads and fully validates the primary: unknown/future versions, invalid format/path metadata, corrupt JSON, oversized files, and missing primary plus existing backup all **fail closed** without overwriting either file. Missing referenced models remain reviewable without scanning or opening them.
- **Migration/rollback boundary:** the operator may create a checkpoint from the existing v1 remembered preference and active model; neither capture nor inspection modifies PlayerPrefs. The old key remains the sole startup restore authority, so declining or discarding the snapshot leaves legacy restore behavior intact. The prior generation is available only for *read-only inspection*; restoring a reviewed `.bak` to primary is an explicit file operation by the operator, not an automatic downgrade. A future change to make this JSON authoritative requires a separate migration, dual-write and rollback acceptance gate.
- The Unity P1 regression validates real session and remembered preference separation; no active model, active/remembered divergence, missing referenced VRM, independent write/backup inspection, rejected unsupported relative/FBX paths, damaged and newer-version primary protection, missing-primary-with-backup protection, file-size limits, and manually restored reviewed backup.

**Deliberate limit:** this is an on-demand checkpoint, not a continuous event log of loads, failures or shutdowns. Snapshots can become stale immediately after capture. No cross-process lock or background watcher is provided. Do not use the checkpoint timestamp or prior active path as proof a model is currently loaded.

## U2.4 — explicit checkpoint adoption, durable rollback and stale-review guard

The old `VCR.Character.LastSuccessfulPath.v1` **remains the sole authoritative startup restore key**. `ModelSessionAdoptionService` adds an explicit, operator-controlled bridge from the versioned U2.3 checkpoint's **remembered** VRM reference to that v1 key. It does not import the checkpoint's `ActivePath`, load/unload a character, alter the original VRM file, or change `--vcr-vrm` precedence. A saved checkpoint is still not consulted automatically on startup.

- In UI Toolkit Sources, **Review remembered VRM adoption** displays the previous and proposed basenames and arms **Adopt reviewed preference** for 20 seconds. Confirmation re-reads the bounded checkpoint, compares its SHA-256 fingerprint with the reviewed bytes and verifies that the v1 key's **presence and value** have not changed. Missing VRM files cannot be adopted (unlike read-only catalog/archival inspection); empty remembered path is an explicit request to delete the v1 preference. A no-op adoption is rejected.
- Before modifying PlayerPrefs, the service atomically writes a versioned `model-session-adoption-rollback.v1.json` containing the previous key's **presence and exact value**, proposed key state, source checkpoint fingerprint, and a `pending` state. This journal is bounded to 32 KiB and keeps a previous `.bak` generation. A corrupt, missing-primary-with-backup, unsupported-version or still-pending journal blocks further adoption. No silent journal replacement or auto-repair.
- **Rollback last adoption** requires two consecutive clicks within 20 seconds. It restores the previous v1 key only when the current key still matches the adopted value (or the old value, indicating a stopped operation before adoption was saved). Unrelated edits from a later manual model action are **never overwritten**. A successful rollback marks the journal `closed`. **Keep adopted preference** likewise requires a double-click and closes the journal without changing the preference, permitting a later deliberate adoption.
- Crash-consistency is intentionally fail-closed rather than an atomic transaction across OS files and PlayerPrefs. A crash after journaling but before the v1 preference write leaves a pending journal; an explicit rollback can safely close it without writing a different preference. A crash after the v1 write but before journal closure can be recovered by manual rollback. A corrupted journal never triggers automatic modification; an operator must inspect files/backup first. **No automatic recovery runs at startup.**
- The Unity P1 real-file/PlayerPrefs regression covers successful adoption, snapshot modification after review, external preference drift after review, pending-journal blocking, later operator edit protection, rollback, empty-preference deletion/restoration, explicit keep, corrupted journal preservation, missing journal primary with backup, and missing referenced VRM rejection. UI wiring and confirmation timing are guarded by source-contract tests.

**Limit:** this operation is not a multi-process compare-and-swap transaction or a service for simultaneous instances; it requires one active editor/Player controlling the profile. A byte-identical source checkpoint and the same v1 key value may still be changed and restored between reads, which cannot be detected without an OS-level lock. The journal is not a replacement for user backups, and an operator should inspect the current/backup files before attempting manual repair. No native Settings adoption action is implied.

## Legacy uGUI retirement — dependency inventory before deletion

The U1 application path retains `ApplicationUiController.cs` and its `NativeSettings` / `MockupDashboard` partials, Unity uGUI inputs and event handling, and older scene/Editor test references. The U2 library shares only the **runtime service and persisted v1 path**, not the legacy UI component. Do not delete the old UI or `com.unity.modules.ui` merely because U2's preference tests pass; removing older scenes, bindings, editor checks or standalone native Settings calls without a whole-repository dependency audit can break P0–P13. Legacy retirement requires a distinct coherent removal diff and exact-source Unity/Windows/macOS rebuild; no release or merge is implied.

## Remaining gate

U2 now has a versioned **manual session checkpoint** and an explicitly confirmed/reversible adoption into the existing v1 restore key. A production authoritative record replacing v1, live load/outcome journaling, fully atomic multi-process migration, and a tested concurrent-writer catalog policy remain separate work. The checkpoint schema version and rollback journal do not deliver automatic state migration. No generic FBX adapter, simultaneous VRM instances, automatic filesystem indexing or source-file upload. Native runtime/CI runs on the exact U2 commit are required before acceptance. Physical U1 verification remains a user-authorized assumption only, not acquired evidence. PR #44 and stacked PR #45 remain Draft/unmerged.
