# Native Windows/macOS Player smoke gate

## Scope

Milestone 5 validates **real standalone binaries** generated by Unity
6000.3.25f1 from an exact commit. This is distinct from the P0–P13
Editor-only test gate and distinct from historical alpha release packages.

Workflow: `.github/workflows/player-native-smoke.yml`. The workflow
builds Windows x64 and macOS Development Players on Linux using the
already pinned MediaPipe, Pretendard, Ultraleap and UniWinC bootstraps,
and then downloads the exact archives to native Windows and macOS
GitHub-hosted runners.

The packaging step requires an actual Player, records archive SHA-256
and source commit, and verifies committed Unity lock/settings files
have not changed during the build. Neither package is published as a
tag/release.

## Native runtime contract

The generated alpha scene includes `PlayerStartupSmoke`. During ordinary
application launches it does nothing. Only
`--vcr-smoke-report=<absolute-json-path>` activates the test.

With `-batchmode -nographics`, the built Player must:

1. Start the real `ApplicationRuntimeBootstrap`, reaching `IsStarted`.
2. Expose an initialized `SingleCharacterSceneRuntime` in `Ready` state.
3. Start with no VRM loaded and without physical tracking hardware.
4. Call **`Application.Quit()` without first calling `Shutdown()`**. Allow
   the application's genuine `OnApplicationQuit` callbacks to save the
   configuration and clean up scene resources.
5. In the ordered smoke `OnApplicationQuit` callback, verify `Stopped`
   and write a JSON report with `quitManagedMilliseconds`. The launcher
   independently records process lifetime and best-effort quit-marker-to-PID-exit
   duration. Missing, prewritten or failed evidence is FAIL.

Previously, smoke explicitly called `bootstrap.Shutdown(false)` first and
then `Application.Quit()`. That bypassed the actual normal-exit cleanup
path, so the historical headless CI runs cannot prove it works.

`tools/run-player-smoke.py` verifies the ZIP source SHA, package digest,
native executable SHA, exact Unity version, runtime report, platform,
exit status, and runtime time limit. On failure it uploads the log and
runner diagnosis; missing JSON is **FAIL**, not an assumed PASS.

## Evidence and exclusions

CI outputs an archive per platform and separate startup/shutdown JSON
plus Player logs. This is **headless native process evidence** only.

It does **not** establish that GUI presentation, transparent windows,
OBS capture, physical camera/tracking, VRM 0.x/1.0 model quality,
Ultraleap, Apple Silicon architecture, or frame-rate targets work.
Those require a later interactive hardware-equipped Windows/macOS
validation pass. A Windows/macOS build alone never counts as a runtime
PASS.

## Diagnosing a slow **visible desktop** close

The headless smoke proves only source-bound native process/managed cleanup.
It cannot reproduce GPU compositor teardown, actual webcam/MediaPipe disposal,
a loaded VRM, a second native Settings window, or the user's desktop session.

Use the same newly built Player executable from the current PR on the affected
Windows or macOS computer and launch the **normal GUI** with the stdlib-only
observer:

```shell
python3 tools/diagnose-gui-shutdown.py "/absolute/path/to/VirtualCharacterRender.exe"
```

On macOS pass the actual executable inside
`VirtualCharacterRender.app/Contents/MacOS/` rather than the .app directory.
Close the application normally; **do not minimize, hide, or kill it**.
The tool collects a `Player.log`, PID lifetime and
`exit-diagnosis.json` in a session folder. On Windows it also samples,
read-only, when Unity/Settings windows cease to be visible.

Interpret the evidence in this order:

- Large time **before** the `quit requested` marker: Unity/UI/native window
  quit dispatch may be blocked before managed shutdown.
- Large gap from marker to `OnApplicationQuit finished`: locate the slow
  `VCR shutdown step end` / MediaPipe native dispose markers with
  `python3 tools/analyze-shutdown-log.py <Player.log>`.
- Small managed shutdown but large marker-to-PID-exit: inspect native Unity
  graphics/audio/input teardown and third-party plugin callbacks/threads.
  Do not attribute such a delay to `sceneRuntime.Shutdown()` without proof.
- If the windows remain visible after managed shutdown, inspect the render
  window lifecycle and compositor instead of hiding them as a workaround.

Repeat unloaded/idle, loaded VRM, active webcam, and Settings-open cases. This
tool **only observes** the process and OS windows. It never hides a window or
intentionally short-circuits application cleanup. Source edits and tests are
development-only; no GitHub Release or version tag is required.

## Windows real-PC evidence — no additional software required

Both Windows native smoke ZIPs now include two scripts alongside the Player:

- `start-exit-diagnostics.cmd` — double-click to launch the GUI Player
  with logging, then exit normally from the program/window control.
- `collect-exit-diagnostics.ps1` — built-in Windows PowerShell 5.1+ collector.
  Does not need Python, an external package, administrator rights, or
  a network service. The optional first argument to the CMD file is an
  absolute path to a different `VirtualCharacterRender.exe`.

The collector launches the **actual visible GUI** using
`-logFile <absolute path>`, records the exit request marker, normal
`OnApplicationQuit` completion, final managed quit callback, process lifetime,
and the moment that its visible Unity/Settings windows disappear. Windows
process termination is observed by `HasExited`, not inferred from a log line.
It captures GPU driver/OS information and matching local Application Error/
Windows Error Reporting events. It never calls ShowWindow to hide a window,
kills the Player, or bypasses native cleanup.

Each session produces `exit-diagnosis.json`, `Player.log`, extracted
`shutdown-events.txt`, `system-summary.txt` and optional
`application-errors.txt`. The generated ZIP is saved under:

```text
%LOCALAPPDATA%\VirtualCharacterRender\ExitDiagnostics\exit-diagnostics-<session>.zip
```

**The ZIP remains on the user's machine and is never uploaded
automatically.** Review it before sharing, since Player.log and crash
reports can include paths, model filenames, or machine information. If the
application does not exit within 180 seconds, the collector records a timeout
and retains the evidence but **does not kill the process**.

Repeat at least three scenarios: (1) cold startup with no character/tracking,
(2) VRM loaded, (3) MediaPipe webcam/tracking active with native Settings open.
The comparison establishes which environment causes the delay.

## Windows native teardown A/B validation

The native CI matrix additionally builds `windows-nodebug` via
`BuildOptions.None`: same source/scene, but no
`BuildOptions.Development` or `BuildOptions.AllowDebugging`.
It runs the same real `Application.Quit` native smoke on a Windows runner.
Compare `quitToProcessExitMs` for `windows` and `windows-nodebug`
inside their respective `runner-evidence.json` files.

This is a diagnostic control to test whether debugger/PlayerConnection
build flags materially affect Windows process termination. It is **not a
replacement for testing the interactive Player on the actual PC**, and it
does not change the existing alpha release packaging or create a release.

## Windows native shutdown stack capture (opt-in)

The 2026-10-16 affected-PC evidence confirmed that runtime shutdown finishes
within tens of milliseconds while the Windows Player remains open for roughly
16.7 seconds. Text logs do not contain the native thread call stack, so they
cannot establish whether Input System, PlayerConnection, DLL unloading,
graphics, or a Unity worker owns that latency.

For **lightweight** diagnostics, run `start-exit-diagnostics.cmd` as before.
It now writes `thread-states.jsonl` at approximately 1, 5, 10 and 15
seconds after the normal quit marker. For every thread, this includes thread
ID, wait state/reason, CPU time and start address where available. It is
observational; it never changes a thread state, hides a window, or kills Unity.

For an **explicitly requested native stack snapshot**, double-click
`start-exit-diagnostics-native.cmd` in the Windows Player ZIP instead.
This calls `collect-exit-diagnostics.ps1 -NativeDump -DumpDelaySeconds 5`,
recording the same lightweight data. If the Player is still alive 5 seconds
after its normal quit marker, a separate built-in PowerShell worker invokes
Windows `dbghelp.dll!MiniDumpWriteDump` to capture one
`native-exit-threads.dmp`. The dump uses `MiniDumpWithThreadInfo` and
`MiniDumpWithUnloadedModules`, **not** full-process-memory flags.
The observer continues polling while capture runs; the actual quit code
and window visibility are unchanged. The dump status and size are recorded
in `exit-diagnosis.json`; absent/failed captures are reported explicitly,
not mistaken for evidence of a fast shutdown.

```powershell
# Equivalent explicit command for an executable in another directory:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\collect-exit-diagnostics.ps1 -PlayerPath "C:\path\to\VirtualCharacterRender.exe" -NativeDump -DumpDelaySeconds 5
```

The minidump is added to the local ZIP only when successfully captured.
**A minidump contains some process stack memory**, which may contain paths,
identifiers, private configuration/model text, or credentials. Do not post
the native ZIP in a public issue or attach it to a public pull request.
Review it and transmit only through an approved private channel.
Ordinary `Player.log` and thread-state metadata may also contain system
paths and should be reviewed before sharing.

The `.dmp` can be opened locally with Microsoft WinDbg. If symbols are
available, `~* kb` lists every native thread stack; `lm` lists loaded
modules. Compare the last steady waiting stack across slow-quit runs,
along with `thread-states.jsonl`. A single stack snapshot is not proof
of the exact duration of an individual native call, and unavailable
third-party symbols may prevent function-level attribution. If the dump
cannot be obtained, retain the timeout/error metadata and do not claim
the root cause has been found.
