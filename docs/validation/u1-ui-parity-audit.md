- `01e6bd0`, strengthened by `645f0c6`: P1 source-free regression creates an actual Unity tracking provider implementing both runtime control and runtime configuration, restores a persisted configuration field and enabled state, verifies same-instance no-op on the next scan, destroys that provider, creates a replacement with the same ID, and verifies both persisted settings and enabled state are applied again exactly once. ## Tracking editor draft vs provider replacement

A separate real-world reconnect risk was found after the restored-instance fix: an operator can open a device's native Settings or UI Toolkit editor, then the device component can be destroyed and replaced by another provider with the same logical ID **while unsaved editor fields remain visible**. Before this fix, both Save handlers rediscovered the current provider by ID and could apply the old provider's draft to the replacement.

- `8af058a`: native Settings now remembers the provider instance that created the editor fields, clears that reference when the device list is rebuilt, and refuses Save if the instance changed. It rebuilds the list and requests that the operator reopen Settings. The UI Toolkit Save closure similarly compares its captured provider with the live current provider, discards the stale editor and reports the issue.
- `2f81270`: the P1 Unity regression verifies that a provider matches itself, rejects a null target and a same-ID replacement, and requires both native and UI Toolkit submission paths to call the identity guard. This uses actual Unity provider fixtures, but **not** native window click simulation.
- This is a protection against applying **stale unsaved drafts to a different runtime instance**. It does not verify that a provider's own recovery implementation preserves live settings on a disconnect that keeps the same component.
- Exact-source CI on these changes and physical device/camera detach–reconnect remain required. Keep status **PENDING** until CI completes.

## Delayed tracking configuration schema and atomic native Add

A configurable tracking source can be discovered before its device-dependent configuration schema is ready. Prior to this fix, if `GetConfigurationSettings()` returned `null`, U1 skipped restoring its stored fields but marked that instance restored. Subsequent scans then skipped it permanently. A separate failure path in native device Add recorded configured/restored membership **before** a required disable was accepted, leaving a stale cache entry on failure.

- `c84a524`: a `null` configuration schema now leaves restoration pending without enabling the provider. The next 2-second scan retries the same instance. An empty **non-null** schema remains valid. Native Add now records membership/restore completion **only after** `TrySetControlEnabled(false)` succeeds.
- `3cd2403`: extend the P1 Unity fixture with a provider that returns `null` once and a persisted setting. Assert first scan does not apply settings or enable, keeps preferences unchanged, and the second scan restores both exactly once; also source-check the native Add ordering.
- This is a simulated delayed-provider condition; actual camera driver startup and native UI click behavior still require physical acceptance.

## Native Settings vs UI Toolkit: schema readiness and live values

Legacy `ApplicationUiController.NativeSettings.ShowNativeTrackingDetails` creates controls using each provider's `TrackingRuntimeSetting.Value` (the live readback). U1 previously preferred `PlayerPrefs.GetString(savedKey, setting.Value)` in both the Native Settings and UI Toolkit editors; these saved values can differ from what is actually applied after a failed restore or an external device change. The new editors also disagreed on `null` schemas: UI Toolkit refused editing, whereas native Settings could open a misleading empty Save form.

- `990ccbe`: unify both editors with `IsWorkspaceTrackingEditableSchema`. A `null` schema is not ready, an empty non-null schema is permitted, and more than 256 fields are rejected. - `994c72e`: both editors now display the provider's **current** `TrackingRuntimeSetting.Value`, not stale PlayerPrefs. Saved settings remain in PlayerPrefs for startup/reconnect restore and are only changed after a successful Apply.
- `97784d5` and `518141d`: P1 validation invokes the shared schema guard for null, empty, exactly 256, and 257 fields; checks a live value is used and requires both editor paths to call the shared guards. Native GUI interaction is **not** exercised by these source-free checks.

## Explicit Tracking recovery must not implicitly enable a source

Source audit found that U1 had two direct `ITrackingRuntimeControl.TryRecover` call sites (Native Settings and UI Toolkit), without checking the user's configured membership or enabled preference. Both built-in MediaPipe and Ultraleap providers can **enable a disabled component inside `TryRecover`**. Clicking Recover on an off or unconfigured device therefore risks unexpectedly enabling its tracking stream while `PlayerPrefs` still says disabled; the restored-instance cache could then suppress correction on later scans.

- `c480edf`: route both native and UI Toolkit Recovery through one `TryRequestWorkspaceTrackingRecovery` helper; require a configured, currently enabled source. Disabled sources must be enabled explicitly via the separate Enable action. Recovery failure is reported without changing persisted preferences or falsely marking success.
- After a successful recovery request, invalidate the saved-state restore marker for that specific provider and defer reapplication of saved configuration and enabled preference until the next two-second restore scan. This also handles same-component restart implementations that discard live settings.
- `0b853ad`: real Unity provider fixture checks that unconfigured and disabled sources cannot trigger recovery; an enabled configured source can recover, the saved preference is unchanged, and an in-place restart which clears runtime settings is restored on the next scan. Also checks a reported recovery failure leaves persisted values untouched and verifies both UI dispatch paths call the shared guard.
- **Validated baseline:** `6011460` Unity P0–P13 / Windows Player [#43569169243](https://github.com/playCosmos/VirtualCharacterRender/actions/runs/43569169243) PASS. AppKit+macOS Player run [#43569137040](https://github.com/playCosmos/VirtualCharacterRender/actions/runs/43569137040) PASS on its identical-code predecessor `0b853ad` (documentation changed afterward).
- **Confirmed duplicate restart:** MediaPipe's `TryRecover()` restarts the webcam, and its `TryApplyConfiguration()` previously called `Restart()` on **every** successful apply while enabled/in Play mode. The U1 post-Recover preference replay therefore restarted the camera again even when the saved capture device, width, height and FPS already matched the live configuration.
- `a167c16`: MediaPipe now calls `Restart()` for actual capture-setting changes or when `_state == Faulted` (explicit retry), not when reapplying identical values. This preserves the saved-settings reconciliation while eliminating an unnecessary second restart for unchanged settings.
- `c4146fa`: P3 source-free fixture creates a MediaPipe runner on an inactive Unity GameObject, checks all four restart-relevant values, applies identical settings, applies a changed width and rejects an invalid width without overwriting the current configuration. A source contract also retains the faulted retry guard.
- **New exact-source CI: PENDING.** Source-free Unity runs cannot prove actual webcam startup timing. Repeated hardware Recover, 720p60/1080p60 OBS capture and long-duration tracking remain physical acceptance requirements.
- **Trade-off:** When saved capture values genuinely differ from the live settings after Recover, the restart remains necessary; a second start may occur. Testing on real hardware must distinguish legitimate reconfiguration from redundant restart.

## Tracking input membership parity: Native vs UI Toolkit Toggle

Static source contract checks both UI call sites and conditional native control registration.

## Saved-off tracking restore must stop capture before applying settings

Restore ordering review found an avoidable runtime side effect: `RestoreWorkspaceTrackingPreferences` previously called `TryApplyConfiguration` **before** applying the persisted enabled preference. On startup, a provider could already be enabled while its saved preference is disabled. Built-in MediaPipe can restart its webcam on changed capture settings, so the old order could start/restart capture only to disable it immediately.

- `31f1943`: read saved enabled preference before provider configuration. If the desired state is Off and the provider is currently enabled, call `TrySetControlEnabled(false)` first. If that fails, do not apply configuration or mark the provider restored; retry on the normal scan. Apply saved fields only after a successful stop. Keep the final enabled-state reconciliation because provider-specific `TryApplyConfiguration` can change runtime enable state.
- `f94c9d0`: the real Unity fixture starts with an enabled test provider but a stored disabled preference. It injects one disable failure and checks that settings were **not** applied on the live camera, that saved preferences are unchanged and the restored marker remains absent. On retry, it asserts disable occurs before configuration, no configuration runs while enabled, final saved settings are applied exactly once and subsequent scans are idempotent.
- This tests component-level sequencing only. Real webcam permission prompts, device driver stop latency and effects on a separate rendering output still require physical testing.
- **Verified baseline:** `b28c813` Unity P0–P13 / Windows Player [#43629911476](https://github.com/playCosmos/VirtualCharacterRender/actions/runs/43629911476) PASS, including the saved-off sequencing fixture. Subsequent ID-case persistence changes require exact-source CI.

## Registered tracking ID casing and PlayerPrefs compatibility

`_workspaceConfiguredTracking` and restored-instance cache use case-insensitive ID comparisons, but the persisted `PlayerPrefs` enabled/setting keys were previously constructed using each **current provider's** literal `ControlId`. A provider that reconnected with a different letter case therefore counted as the same configured source, but the saved value lookup could miss the original key and silently fall back to disabled/default configuration. Native and UI Toolkit toggles/saves could further write to the new spelling while the configured ID list retained the old one.

- `8d597ab`: `GetWorkspaceTrackingPersistenceId` resolves the original registered spelling from the configured ID set. Restore reads, Native Settings/Toolkit setting saves, Toggle, Add/Remove all use that spelling; remove resolves it **before** removing membership. New sources use their own ID until registered. Restored-provider identity comparisons remain case-insensitive, preserving the earlier reconnect behavior.
- `6781e2e`: P1 Unity test registers a mixed-case ID, stores enabled/settings under that spelling, connects a lowercase provider, verifies both settings and enable restore, toggles Off/On with the original persisted key, and reattaches another lowercase provider. Native/Toolkit membership-remove paths are source-checked for canonicalized preference writes.
- This does **not** attempt to migrate older split-case preference entries already produced by the previous bug; automatically reconciling conflicting settings under multiple arbitrary spellings would be ambiguous. Actual provider identity stability across hardware reconnect still needs verification.
- **Validation:** exact-head Unity P0–P13 and Windows Player pending; prior `b28c813` [Unity #43629911476](https://github.com/playCosmos/VirtualCharacterRender/actions/runs/43629911476) PASS, Repository Push/PR #43629911439/#43629915926 PASS.

## Tracking configuration Save must not implicitly re-register a removed device

The native Settings and UI Toolkit configuration editors correctly bound their fields to a specific provider instance, but **not to the configured-membership state**. If another Settings surface removed a provider while an editor remained open, the old Save action could still call `TryApplyConfiguration`, write preferences, then silently insert the provider back into `_workspaceConfiguredTracking`. ## Membership Stop requires confirmed disabled readback

The tracker control interface exposes both a Boolean Stop acknowledgment and a separate `ControlEnabled` property. Previously `TryStopWorkspaceTrackingForMembership` accepted `TrySetControlEnabled(false)` returning `true` without checking whether capture actually turned Off.
